# Conventional Commits, Conventional Branch e standard di pubblicazione

Stato: accettata il 26 settembre 2026 per Q01 (#188).

Trama scrive nel repository di un progetto il commit di un candidato, il branch dello sviluppatore, la pull request e, in un progetto nuovo, il primo commit. Prima di Q01 il commit usava il titolo dell'incarico così com'era, i branch si chiamavano `trama/<nome>-<id>` e il titolo della pull request non seguiva una convenzione.

Decisione:

- **Prima le regole del progetto.** Trama legge `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` (anche in `.github/` e `docs/`), la configurazione di commitlint (`.commitlintrc*`, `commitlint.config.*`, la chiave `commitlint` di `package.json`) e i prefissi dei branch esistenti. Le configurazioni JavaScript si leggono come testo e non si eseguono; i collegamenti simbolici non si leggono. Le regole dichiarate valgono più dei prefissi dei branch esistenti, che valgono più dei default. La scheda del candidato dice da dove vengono le regole.
- **Default: Conventional Commits 1.0.0.** Tipi `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`, `style`, `revert`. Il tipo viene dal tipo di lavoro (funzione nuova e ticket concordato `feat`, correzione `fix`, compromesso `refactor`) e dai file: un lavoro che tocca solo documentazione, test, CI o file di build prende `docs`, `test`, `ci` o `build`. L'ambito è l'unico modulo toccato; con più moduli non c'è ambito. La descrizione viene dalla fetta o dall'obiettivo, il corpo spiega il perché, il footer porta `Refs: #N` e `Trama-Candidate: <id>`. Una modifica incompatibile usa `!` e il footer `BREAKING CHANGE:`.
- **Il Coordinatore corregge, Trama convalida.** Il Coordinatore sceglie tipo, ambito e hotfix con `assign_task` e corregge il messaggio con `set_commit_message`. Trama convalida ogni messaggio con le regole della specifica (tipo, ambito tra parentesi, due punti e spazio, riga vuota prima del corpo, token dei footer con i trattini, `BREAKING CHANGE` in maiuscolo, `BREAKING-CHANGE` come sinonimo, unità non sensibili alle maiuscole) e con quelle del progetto (tipi, ambiti, lunghezza del titolo). Un messaggio non valido viene rifiutato con cosa non va, prima del commit. Il primo commit di un progetto nuovo è `chore: start the project`.
- **Branch in Conventional Branch.** Il nome è `<tipo>/[issue-N-]<descrizione>-trama-<id>`: `feature/` per una funzione nuova, `bugfix/` per una correzione, `hotfix/` per una correzione urgente, `chore/` per documentazione e manutenzione; `release/` è riconosciuto. Trama riconosce anche `feat/` e `fix/` e li usa se il progetto li usa. Solo minuscole, cifre e trattini, i punti solo nelle versioni di `release/`, niente trattini o punti ripetuti o in testa o in coda. La fine `-trama-<id>` rende il branch riconoscibile e unico; Trama controlla anche i branch locali e remoti e convalida il nome prima di crearlo. I branch `trama/` creati prima restano riconosciuti.
- **La pull request.** Il titolo è il titolo del commit. Il corpo dice cosa cambia, le verifiche di Trama con l'esito, i seam testati come dichiarazione dello sviluppatore, le decisioni del Patto, i limiti e la issue. La issue è collegata con `Refs`, non con `Closes`: Trama chiude una issue solo con le evidenze (C10).
- **Standard di pubblicazione.** Trama apre la pull request solo se il candidato è verificato (V05), il messaggio è valido, non ci sono segreti né file sensibili nelle righe aggiunte e nei file cambiati, `git diff --check` è pulito, la issue è collegata quando esiste (una fetta senza la sua issue su GitHub non lo è) e nessuna domanda del Patto sul lavoro è aperta. `git diff --check` gira alla dichiarazione del candidato, sui file tracciati e su quelli nuovi. Prima del commit Trama svuota l'indice e vi aggiunge solo i file del candidato: un file sensibile già in staging non entra nel commit. La issue di una fetta è la sua, mai quella del piano. Le regole di commitlint disattivate (severità 0) non valgono. La scheda del candidato mostra ogni condizione e come sistemare quelle che mancano; il pulsante per preparare la pull request compare solo quando non manca niente.

Conseguenze: un candidato dichiarato prima di Q01 non ha il controllo di `git diff --check` e chiede un nuovo candidato. Il testo della descrizione resta nella lingua del progetto: Trama non traduce, e un'imperativa corretta dipende dal titolo della fetta o dalla correzione del Coordinatore.

Alternative scartate: eseguire commitlint o le sue configurazioni JavaScript, che esegue codice del progetto fuori dalla sandbox; `Closes #N` nel commit, che chiuderebbe la issue al merge senza le evidenze di C10; tenere `trama/` come prefisso, che ignora le convenzioni del progetto.
